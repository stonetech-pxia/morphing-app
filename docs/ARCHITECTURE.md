## 1. Layers and module boundaries

```
┌───────────────────────────────────────────────────────────────┐
│ apps/mobile (Expo / React Native)                               │
│  src/app/        routes: home, [pageId], tool catalog, history,   │
│                  settings, AI changes                            │
│  src/renderer/   whitelisted component table: config type → real │
│                  component                                       │
│  src/storage/    SQLite: revisions, change requests, files,      │
│                  grants, run records                             │
│  src/runtime/    workflow runner + platform actions (pick files, │
│                  save, share)                                    │
│  src/share/      share to Morph: receiving, inbox                │
│  modules/morph-vision/  local native module (iOS Swift: Vision;  │
│                  Android Kotlin: ML Kit)                         │
│  plugins/        local config plugin (controller of the iOS      │
│                  share extension)                                │
│  modules/morph-share/   share several files at once, save to a   │
│                  chosen folder                                   │
│  modules/morph-media/   video (audio later): iOS AVFoundation,   │
│                  Android Media3 Transformer                      │
│  ios/ android/   generated by expo prebuild (CNG, not in git)    │
├───────────────────────────────────────────────────────────────┤
│ packages/core (pure TypeScript, no platform dependencies)        │
│  schema · operations (ops) · apply · validate · migrate ·        │
│  change description (describe) · AIProvider interface · mock AI  │
├───────────────────────────────────────────────────────────────┤
│ packages/tool-*  pdf (pdf-lib) · image · archive (fflate) · qr   │
│                  pure logic, manifests in core/src/tools         │
├───────────────────────────────────────────────────────────────┤
│ apps/api (M3)  Hono relay + Claude (accounts and cloud data: see │
│                CLOUD_DESIGN)                                     │
└───────────────────────────────────────────────────────────────┘
```

Dependency rules:

- `core` must not import React, React Native, Expo or any platform API. All logic that can be tested on a computer lives here.
- `tool-*` depends only on the types and action interfaces of `core`; platform abilities such as reading and writing files are injected by the app.
- `apps/mobile` depends on `core` and `tool-*`; the renderer may only render whitelisted components and never executes any code from the config.
- Native code is written only in local Expo modules (`apps/mobile/modules/`) and uses only system frameworks (exception: the controller of the iOS share extension lives in `apps/mobile/plugins/share-extension/` and is put into the generated extension target by a config plugin, D-118). On the JS side, use `requireOptionalNativeModule`; when the module does not exist (Expo Go, Android, tests) it is `null`, and callers must have a fallback.
- The AI (mock or real) can only output a **list of operations**. It cannot write the config, write the database or generate code directly.

## 2. Fixed core and variable layer (§5)

| Fixed core (the AI cannot change)                                                                             | Variable layer (the AI changes through operations)  |
| ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Renderer and component whitelist, validator, migrations, storage, runner, action registry, protected elements | Pages and component tree, navigation, theme, layout |
| Tool code (ships with the app)                                                                                | Tool install state, tool settings, workflows        |

Protected elements (§5.1): only "Settings" must stay in the navigation bar or the floating buttons, enforced by the `core` validator. The settings page always provides three entries from the fixed core: "Change this app", "Change history" and "Tools". So AI changes, history and tools can be removed from the navigation bar entirely, and changing and undoing remain possible at any time (DECISIONS D-031).

What the AI can change (schemaVersion 2, see `packages/core/src/schema.ts`):

- **Style**: primary color, light/dark mode, background / card / text / secondary / third colors (dark mode can be colored separately, schemaVersion 6), font (Clay / system / serif / monospace), font size scale, corner radius, density, card style (shadow / outline / flat / neo-brutalist / neumorphic / clay / frosted glass / neon glow / metal), page background (solid / gradient / aurora), navigation bar style (icon + text / text only / icon only). Themes whose body text contrast is below 4.5:1 are rejected by the validator.
- **Components**: title, text, tool card, add-tool entry, file list, workflow runner, button, shortcut card, callout, divider, spacer, and groups (vertical / horizontal / 2–3 column grid, no nesting); each component can have alignment, tone and size, and can be hidden.
- **Pages**: create, delete (except the home page and the tool page), rename, change icon; the navigation bar has 1–5 items and there are at most 3 floating buttons, which can point to any page or system entry.
- **Images and rich text** (schemaVersion 4): image slots (the user picks the photo), bold / italic / links / lists in text and callouts, emoji icons (D-044–D-048).
- **Table structure** (schemaVersion 3): the AI can create tables and add, remove and change fields, and show them with three components: record list, quick-add form and stat (see [DATA_DESIGN.md](DATA_DESIGN.md)).
- **Cannot change**: components and properties outside the whitelist, arbitrary code, the content of system pages (settings, tool catalog, history, data, AI changes page, record edit page), the code and actions of tools, and **the content of user records**.

Direct editing (D-235, reusing the draft protocol of D-052–D-059): a long press selects just one component, and the same touch can drag it to reorder, keeping the page's grid and group layout; the "Edit" next to the selected item opens the panel for text, look, hide, delete and position. The whole-page "Edit" button stays off, and the old ArrangeView is kept (`apps/mobile/src/editing/`). The UI only translates gestures into the same operations (the computation of move up / move down / drag-and-drop and the merging of adjacent operations are in `core/src/arrange.ts`); each step is validated into the draft first, and "Done" combines them into one version. What can be changed is a subset of the list above: only components on navigation-bar pages and standalone pages, no system pages, and no text or records of data components.

User records (DATA_DESIGN.md): stored in the `records` table of the local database, not in the config, not restored with versions, and never sent to the AI. The user adds, deletes and edits them directly on the page (`apps/mobile/src/data/records.ts`), which does not create versions.

## 3. Change flow (§7D, D-190, D-191)

The AI's changes take two paths (`core/src/ai/kinds.ts`, `change` in `workspace/store`):

- **Look changes** (changing style, the position and text of blocks on a page, and the like) go into a **draft** first (D-190): the app shows how it looks after the change while the saved version stays as it was; only when the user taps "Apply" is one version created.
- **Feature changes** (D-191: creating tables, fields, adding / removing / changing quick actions, adding / removing tools, ...) **take effect directly** and are recorded as one version with `source: 'ai'`, which can be undone at any time in "Change history" (invariant 7, D-378).

```
User input                                     (direct editing: long press / drag / arrows yield ops directly, skipping the AI, see below)
  → AIProvider.plan(input, trimmed summary of the current config)  → operation list ops
  → core.prepareOps / apply(current config, ops)  → candidate config
  → core.validate(candidate config)               structure / references / permissions / protected elements
  ├─ look: into the draft (the user can keep talking to the AI and change more), on "Apply" → storage.commit
  └─ feature: directly → storage.commit(baseRevisionId, candidate config)  SQLite transaction: written only if head still equals base
  → re-read head from the database → render
       ├─ success: show "Applied", can be undone
       └─ failure: automatically commit "the previous config" as a new revision, ChangeRequest marked rolled_back
```

Both undo and restore commit the old config as a **new revision**; history is append-only.

Changes made from the UI (install / uninstall a tool, pick a photo, direct editing) call `store.proposeOps(ops, summary)`, go through the same apply + validate, and are recorded as a revision with `source: 'user'`; the banner can undo them in the same way. Installing / uninstalling a tool first shows a dialog listing the change description and then asks for confirmation; picking a photo is confirmed directly; direct editing submits the whole draft as one change when "Done" is tapped (the result is already in front of the user, so no preview page is shown). Restoring an old version is also a change: it asks once, takes effect immediately after confirmation, and the Change history page pages back from the most recent, all the way to the first version.

## 4. Startup flow

```
read head revision → migrate step by step by schemaVersion → validate
  ├─ pass: render
  └─ fail: walk back through history to the last valid revision and render it, write a log (no blank screen)
```

On first launch, the built-in default workspace is written as revision 1.

## 5. Local storage (the only authoritative source for M1/M2)

SQLite tables (`PRAGMA user_version` manages database structure upgrades, see `apps/mobile/src/storage/sqlite.ts`):

| Table             | Contents                                                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| `workspace_head`  | ID of the current head revision                                                                               |
| `revisions`       | Immutable snapshots: ID, parent ID, schemaVersion, config JSON, source, summary, time                         |
| `change_requests` | Original input, ops, status, linked revision, error                                                           |
| `assets`          | User file metadata and local path (belongs to the workspace)                                                  |
| `asset_grants`    | Tool → file grants                                                                                            |
| `tool_runs`       | Workflow run records (no file contents)                                                                       |
| `app_meta`        | Small on-device settings, for example usage statistics (D-127); not in the config, not restored with versions |

User files are stored in the app document directory at `assets/<id>/<file name>`, separate from revisions; rollback and uninstalling tools never touch them.

## 5.1 Workflow execution (TOOLS_DESIGN.md)

The runner is in `packages/core/src/workflow/engine.ts`: it executes steps in order and passes **one typed value** between steps (images / pdf / files / zip / text / records, D-060). Before running it checks the type chain and parameters once more, and it supports progress, cancellation, asking for parameters at run time, and pack confirmation; `tool_runs` records only status and error codes. The action contract (input and output types, zod parameters, parameter UI metadata) is in `core/src/workflow/contract.ts` and in the tool manifests.

App side: `apps/mobile/src/runtime/runner.ts` connects the runner to storage and the platform; the action implementations are in `runtime/actions/`, and pure logic calls `packages/tool-*` (tool-pdf, tool-image, tool-archive, tool-qr, tested in Node with real files); platform abilities (pick photos / files, temporary files, share, save to the photo library, print) are injected through `FilePlatform` (`runtime/platform.ts`), implemented by Expo modules in the app and by an in-memory implementation in tests. The run page `app/run/[workflowId].tsx` shows each step, the local operation UI (`run/local/`) and the result preview. Intermediate results are temporary files in the cache directory `runs/<runId>/`, and only "Save" turns them into user files (D-063).

Workflow management (D-081, D-082): presets are written in `core/src/workflows/presets.ts` and copied into the config with `presetWorkflow()` when added; add, delete and change are all operations (`addWorkflow`, `updateWorkflow` and so on, in `core/src/ops.ts`), and like the AI they go through validation, create versions and can be undone. The "Workflows" page `app/workflows.tsx` (`shell/WorkflowsScreen.tsx`) lists my workflows, the preset library and those that come with tools; the edit page `app/workflow/[id].tsx` (`run/WorkflowEditor.tsx`) builds a form from an action's `fields` (`run/ParamForm.tsx`) and lists only actions whose types fit (`insertableActions`), and saving goes through `run/workflow-change.ts` (proposeOps → confirm, no preview popup any more). These two pages are provided by the core and the AI cannot change them. The mock AI's workflow phrasings are in `core/src/ai/workflow-phrases.ts`.

Packs (D-064, D-075): the manifest is in `core/src/packs.ts`; download, verification and deletion are in `apps/mobile/src/packs/store.ts` (`documentDirectory/packs/<id>/<version>/`); `PackHost` mounts a hidden WebView on demand, the pages are fixed HTML shipped with the app (`packs/pages/`), and library files are sent into the page in chunks through `bridge.ts`. The download starts only after the user confirms in `PackGate`; "Settings → Downloads" (`app/packs.tsx`) manages downloaded packs. Pack pages: `pdfview` (pdf.js), `scan` (OpenCV.js + jscanify: edge detection, perspective correction), `ocr` (tesseract.js: the worker is a Blob assembled from a prelude script, a core with embedded wasm, and worker.min.js; the language data is sent into the worker by the page). Images sent into a page are first re-encoded to JPG in the app and scaled down to within 16.77 million pixels (`imageForPage`); when leaving the run page, the scan and recognition pages are closed to free memory. When an action's pack is determined by a parameter, use `packFor` (the runner asks for parameters first, then confirms the download).

System recognition (D-084–D-087): `FilePlatform.vision` (`VisionPlatform`, interface in `runtime/platform.ts`, implementation in `runtime/expo-vision.ts`) wraps the local module `MorphVision` (iOS: `modules/morph-vision/ios/MorphVisionModule.swift`; Android: `modules/morph-vision/android/…/MorphVisionModule.kt`, ML Kit, without edge detection and straightening): `recognizeText` (Vision text recognition), `findPaper` (document segmentation + rectangle detection), `straighten` (Core Image perspective correction, written directly into this run's temporary directory), `scanDocuments` (the VisionKit document camera). When `vision` is `null` (Expo Go), `canFindPaper` is false (Android) or `supportsLanguage` is false (Russian on Android), `scan.detect` / `ocr.recognize` fall back to the scan pack / text recognition pack; the runner decides through `packNotNeeded` in `runner.ts` whether this step needs pack confirmation. In tests, `FakeFiles.vision` is `null` by default; replacing it with `FakeVision` gives the iOS path, and additionally setting `canFindPaper = false` and adding `ru` to `unsupported` gives Android.

Share to Morph (D-114–D-118, TOOLS_DESIGN §11): the native part is expo-share-intent (iOS share extension + App Group, Android intent-filter), and the iOS extension's controller is our own. `share/useIncomingShare.ts` in the root layout subscribes to the native module, and `share/incoming.ts` turns the data of the two platforms into the same `PickedFile[]` the pickers produce, kept only in memory; the inbox `app/share.tsx` (`share/ShareScreen.tsx`, a core page) uses `shareFit` in `core/src/share.ts` to list the workflows whose first step fits, and tapping one jumps to `/run/<id>?shared=<share ID>`; `startRun({ incoming })` hands the files to the first step's `in.photos` / `in.files`, which then no longer open a picker. The copies in the shared directory are deleted by `FilePlatform.removeShared`.

Output destinations (D-119, D-120): `FilePlatform.shareUris` / `saveToFolder` are implemented by `runtime/expo-share.ts`, which wraps the local module `MorphShare` (`modules/morph-share/`: on iOS `UIActivityViewController` and folder picking + `NSFileCoordinator` copy; on Android `ACTION_SEND_MULTIPLE` + the module's own FileProvider and the Storage Access Framework). When the module is `null` (Expo Go), sharing falls back to opening files one by one with expo-sharing, and saving to a folder falls back to `Directory.pickDirectoryAsync` of expo-file-system. The remembered folder (D-123) is stored by the native module (iOS bookmark in UserDefaults, Android persistent permission + SharedPreferences), and JS gets only the folder name (`rememberedFolder()`); in Expo Go it is remembered only in memory. All dependencies are passed in as parameters, `__tests__/expo-share-test.ts` tests both paths with a fake native module; actions and the result page use `FakeFiles.shareSheets` / `folderChoice` / `folder`.

Video and audio (D-140–D-148): `FilePlatform.media` (`MediaPlatform`, interface in `runtime/platform.ts`, implementation in `runtime/expo-media.ts`) wraps the local module `MorphMedia` (`modules/morph-media/`: on iOS `AVAssetReader` + `AVVideoComposition` + `AVAssetWriter`, Passthrough export, `AVAssetImageGenerator`; on Android Media3 Transformer 1.9.1 and MediaExtractor / MediaMetadataRetriever). The JS interface is designed for video + audio (`probe`, `transcode`, `trim`, `thumbnails`, `cancel`, `progress` events; `concat` and `waveform` are left for audio tools). Bitrate and resolution are computed in `core/src/media.ts` (pure functions, Node tests), and the actions are in `runtime/actions/video.ts`; the screen stays on during processing, progress is shown as a percentage, and "Stop" cancels the native task. Videos are not copied into the run directory: `FilePlatform.adoptIntoRun` moves the copy from the picker cache in, and shared-in files are used in place. The video / audio row on the result page is `run/MediaRow.tsx` (expo-video playback), and trimming a clip is `run/local/TrimScreen.tsx`. When the module is `null` (Expo Go), video actions report `needsFullApp`; in tests `FakeFiles.media` is `FakeMedia` (computes output size from the bitrate). PDF compression (D-145) needs no native code: `packages/tool-pdf/src/compress.ts` finds JPEG / Flate images and hands them to the system encoder, `runtime/actions/pdf-compress.ts` searches for quality and scale and asks the user with `LocalUi.choose` when it cannot compress enough, and converting to images uses the PDF preview download content.

Image composition (long stitched image, grid, mosaic, watermark, photo paper): layout is in `packages/tool-image`, `runtime/actions/compose.ts` generates a fixed set of drawing steps (`DrawOp`), and `runtime/skia.ts` executes them off screen. Exceeding the GPU canvas limit crashes the app outright (it is not a JS error), so every canvas first goes through `surfaceScale`. Text to PDF and reports use the fixed templates in `core/src/html.ts` + expo-print.

## 6. External capability interfaces (§14.2)

- The AI source is chosen in "Settings → Tink" (`apps/mobile/src/ai/`): built-in rules / Morph server / your own key (Anthropic or an OpenAI-compatible API, D-241). The planning logic is in `packages/planner` and all runs inside the app (D-193).
- `AIProvider` (implemented):
  - mock: rule-based parsing, works offline (phrasings in [MOCK_AI_PHRASES.md](MOCK_AI_PHRASES.md)).
  - Claude planner: `packages/planner/src/planner.ts` writes the prompt in the app (using the local registry, including downloaded tools), validates (`PlanSchema` + `prepareOps`), and when the result is unacceptable it asks once more for a correction, with the list of problems. The transport for model calls is one of three: with your own key, it calls the Claude HTTP API directly (`packages/planner/src/http.ts`) or an OpenAI-compatible API (`packages/planner/src/openai.ts`); with the Morph server, it is relayed through `POST /v1/complete` (`packages/planner/src/relay.ts`, app side in `apps/mobile/src/workspace/remote-ai.ts`). When the service is unavailable it returns a refusal saying "no changes were made" and never silently falls back to the mock.
- Whatever the source, once a plan reaches the app it goes through `PlanSchema` and `prepareOps` again (§8: model output is never trusted directly).
- Eval: `packages/core/src/ai/eval-cases.ts` is the eval set shared by the mock and the real model; `npm run eval -- --model <id>` runs it with a real model (small cost) and by default takes the same relay path as the Morph server mode.
- The following only fix a shape, with no code: `SyncProvider` (cross-device sync), `StorageProvider` (cloud files), `ExecutionProvider` (whether actions run locally or in the cloud). For the design of accounts and sync see [CLOUD_DESIGN.md](CLOUD_DESIGN.md).

## 7. Model relay (apps/api, D-193)

```
App (writes the prompt, validates, corrects) ──POST /v1/complete {system, messages}──► Cloudflare tunnel ──► Hono (127.0.0.1)
        client token → request shape (only system and 1 / 3 messages, user messages must be text, ≤320KB)
        → global daily spend cap → this device: count of replies that do not look like a plan, count per minute, spend per day
        → Claude (model, output cap and thinking effort are set by the server; system prompt marked for caching)
        ◄── {text, stopReason, content, model, usage} or {error: unauthorized | bad_request | blocked | rate_limited | daily_limit | ai_unavailable}
```

- The server does not know the schema, tools or prompts: no matter how the app is upgraded, the server need not change. The cost is that prompt changes have to ship with the app.
- Limits are computed in money (prices in `packages/planner/src/models.ts`): `MORPH_DEVICE_DAILY_USD` per device per day, `MORPH_GLOBAL_DAILY_USD` for all devices per day. A reply that is not "JSON with a kind" counts once; when a device exceeds `MORPH_OFF_PLAN_LIMIT` such replies in a day, nothing more is relayed that day (a model refusal does not count).
- When `ANTHROPIC_API_KEY` is not configured, `/v1/complete` returns 503 (the built-in rules in the app do not need the server).
- It listens only on `127.0.0.1`; logs record only metadata (turns, tokens, cost, duration, the first 8 characters of the device id hash) and never the prompt, user input or reply.
- Production is deployed on a Mac mini and exposed through a Cloudflare tunnel (D-131, [DEPLOY.md](DEPLOY.md)); before login and device attestation (P-024) go live, it is protected by the client token + the limits above (D-132).

## 7. The 5 biggest engineering risks

| Risk                                                                                                                        | Response                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. The declarative DSL gradually bloats into "another programming language", is hard to validate, and risks store rejection | Workflows stay linear and non-Turing-complete; any new component or action must go through code review and into the whitelist                                                                                           |
| 2. After schema evolution, old revisions cannot be restored                                                                 | Write a migrate function + tests for every upgrade; keep a fixture for every historical version as a migration regression test                                                                                          |
| 3. The mock AI makes people overestimate the real AI                                                                        | The phrasing list is the acceptance bar; M3 uses the same phrasings as the eval set for the real model                                                                                                                  |
| 4. pdf-lib runs out of memory on large files on a phone                                                                     | File size limits (P-006, `core/src/limits.ts`, all entry points go through the same `checkSizes`); give a clear message when exceeded; files never leave the phone (invariant 1), so they are never handed to the cloud |
| 5. Expo SDK upgrades are frequent and may bring breaking changes                                                            | `core` does not depend on Expo; keep the app layer thin; regenerate the native projects with CNG; run `expo-doctor` and all tests before upgrading                                                                      |

## 9. Overview of write paths (who writes what, and how it is protected)

| What is written                  | Who, from where                                                                                                                                                                                               | How it is protected                                                                                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Config (`revisions`)             | The AI's feature changes / draft "Apply" / UI actions / restoring an old version, all through `workspace/store` → `commitRevision`                                                                            | Validation; written in a SQLite transaction only if head still equals base; append-only, any version can be returned to (Change history pages back to the first one)            |
| One record (form)                | `update` in `data/records.ts` → `Repo.updateRecordIfUnchanged`                                                                                                                                                | Conditional write against the values when the form was opened (check + write in one transaction); if changed elsewhere, ask the user: keep my changes / use the latest / cancel |
| Record (tick on the list)        | `patch` in `data/records.ts`                                                                                                                                                                                  | Changes the record as currently stored, touching only the ticked item                                                                                                           |
| Records (bulk setAll)            | `data/record-actions.ts` → `Repo.applyRecordWrites`                                                                                                                                                           | Ask first; change all or none in one transaction; anything changed elsewhere in the meantime is not overwritten at confirmation                                                 |
| Record (notification button)     | `reminders/reminder-actions.ts`                                                                                                                                                                               | The record write and the "this tap has been handled" mark are in the same transaction; if the write fails the button can be tapped again                                        |
| Record (home-screen widget)      | `widgets/useWidgets.ts`: native `readQueue` (does not delete) → run one by one and record marks → `removeQueue`                                                                                               | If an error occurs midway, what was not done stays in the queue; if deletion fails, re-reading will not do anything twice                                                       |
| User files (copied into the app) | `storage/copy-files.ts` (picked), `storage/keep-files.ts` (opened / shared in; the same name and size also need the same content SHA-256 to count as the same file), `user-files.ts`, `runtime/actions/io.ts` | The original is untouched; if registering fails after copying, the new copy is deleted                                                                                          |
| Desk (`desk/<id>/`)              | `desk/store.ts`                                                                                                                                                                                               | `desk.json` and `editing.json` are first written completely to `.tmp` and then swapped in, with the old one kept as `.bak`; if corrupt on read, fall back to `.tmp` / `.bak`    |
| Model relay quota (apps/api)     | `apps/api/src/server.ts`                                                                                                                                                                                      | There is no `await` between the admission check and registration; in-flight requests reserve cost at the output cap first and settle at the actual cost when done               |

The storage layer (`apps/mobile/src/storage/`) does not depend on the renderer, the shell, the edit pages or the action runner (ESLint rule); the small functions it needs are in the leaf modules `runtime/ids.ts`, `mime.ts`, `pdf-errors.ts`, `platform.ts`.
