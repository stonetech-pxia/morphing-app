# Re-test of text classification with variable categories

`cases.jsonl` holds 60 hand-written fictional Chinese, English and French OCR texts: 3 each for 19 document kinds, plus 3 that cannot be recognized. Topics span dining, shopping, housing, work, travel, entertainment, education, health, finance, government and personal life. Kind and topic are two dimensions that can both apply, for example "dining order" and "dining receipt". All texts are also rendered as `images/*.png` and saved as `files/*.txt`, for re-testing the native OCR and file-reading paths. The images are generated by `render_cases.py`; **the committed images are the baseline for re-testing**, since fonts across platforms do not guarantee identical pixels.

This is a small synthetic screen, not real-world accuracy. There is only one example per kind per language, and some topics could reasonably have more than one right answer; scoring uses only the preset single ground truth. `evaluate.py --noise` randomly drops some words/characters with a fixed seed. It is a diagnostic perturbation and cannot stand in for the actual error distribution of ML Kit/Vision. Image file names contain the category, so when feeding a model, pass only the OCR text, never the file name, path or ground truth. Blank OCR must be checked separately for whether the model can reject it.

Two kinds of candidates: a zero-shot NLI model judges each user-supplied candidate category in turn; an embedding model compares the similarity of the OCR text to the user's category descriptions. They **cannot invent new category names on their own**, but they can accept new user category descriptions without retraining weights. `evaluate_qwen.py --mode free` tests free naming on the existing Qwen3.5 generative model; that output must be normalized, deduplicated and confirmed by the user. The candidate names/descriptions used in the eval are in `KINDS` and `TOPICS` in `evaluate.py` and can be changed to user-defined categories and re-tested. Raw model results, weights and virtual environments are in the ignored `../models/` and `../results/`; reports and handoff notes are not in Git.

Jev-style decision models have their own `evaluate_decision.py` (Laya multilingual) and `evaluate_kev.py` (Kev 0.8B). Both score each candidate category directly and cannot generate new categories; one run tests "document kind" and one tests "topic". For completely blank OCR the scripts reject in code; other unreadable text still goes to the model. `--unknown-option` adds "cannot tell" to both candidate sets, to test whether non-empty garbage can be rejected and what share of readable text is wrongly rejected. **The original test without this flag has no reject option and cannot be used to judge a model's ability to reject.** `--noise` uses the same fixed perturbation as above. Exact versions and licenses are in `decision_models.json`. Kev's `LocalPredictor` needs a compatibility layer for the `fcntl` import in the script on Windows; it does not use Unix file locking. `label` is only a placeholder for the official record format, and Kev's `materialize` does not encode it into the model input. Phone compatibility, memory and latency are all unverified.

The sources, revisions and weight SHA-256 values of the embedding/NLI models are in `classification/models.json`; GGUF sources and hashes are in the parent `models.json`. `classification/download.py` downloads the given revision, checks the hash and places it in the ignored `models/`. These classification candidates only handle text. The raw Qwen3 Embedding safetensors are about 1.19 GB and the raw BGE-M3 weights about 2.27 GB; whether they can be quantized and run within a phone budget needs native measurement. GGUF results on a desktop GPU cannot stand in for phone RAM, timing or real OCR results.

`evaluate_embedding_gguf.py` uses llama.cpp's `--embedding --pooling last`, adds the same English task instruction to the query as the float version, and precomputes the candidate category vectors. `--model q4` uses a third-party Q4 package and `--model q8` uses Qwen's official Q8 package; both versions must re-run the same test, and the float version's results must not be applied to them directly. The script starts and cleans up its own local server, default port 8096; make sure the port is free. Process working-set samples and classification results are written to the ignored `results/classification/`. This is still a desktop CPU result and does not represent native phone performance.

## Task 124: calibrate "cannot tell" on an independent set, and match the user's tables and quick actions

The report is not in the repository (measurement results do not go into git); it is at `side-session-notes/model-eval/CLASSIFY_124_REPORT.md` on this machine.

- `holdout/cases.jsonl`: 114 newly written fictional OCR texts (38 each in Chinese, English and French), written separately by someone who had not seen the 60 above, not rewrites. It includes documents without a title, different documents from the same merchant, out-of-scope files (kind `none`), partly recognized text, blank text and garbage. `split` separates the calibration set from the test set, and the same `group` (same merchant / layout) is only on one side.
- `evaluate_holdout.py`: blank text and garbage are first rejected by the app's `textReadability` (`packages/core/src/text-classify.ts`, called through `ts_features.ts` using the same TS code); the rest is scored by dimension with the Qwen3-Embedding GGUF, `min_score` / `min_margin` are set on the calibration set, and only the test set reports correct, misclassified, rejected and wrongly rejected, split by language and sample type.
- `match/`: `profiles.json` (6 fictional users: tables are in `CollectionSchema` format, quick actions have only names), `presets.json` (the 4 content-based built-in quick actions exported by `export_presets.ts` from `workflows/presets.ts`), `docs.jsonl` (90 file texts and the recommendations each user would accept; empty = nothing should be recommended). `evaluate_match.py --backend baseline` uses no model (keywords + `text-rules` hits + file type), and `--backend embedding` uses the same Embedding; thresholds are all set on the calibration set.
- `calibrate.py`, `llama_embed.py`: the calibration and llama-server management shared by both sides. `test_calibrate.py` is their unit test; the fake vectors only exercise the code and are not results.

```bash
# Run npm ci at the repository root first (ts_features.ts needs tsx); then run from tests/local-model-eval/
python -m unittest discover -s classification -p "test_*.py"
python classification/evaluate_match.py --backend baseline
python classification/download.py qwen3-embedding-q8
MORPH_LLAMA_SERVER_BIN=/abs/llama-server python classification/evaluate_embedding_gguf.py --model q8   # first reproduce 49/57, 45/57
MORPH_LLAMA_SERVER_BIN=/abs/llama-server python classification/evaluate_holdout.py --model q8

```
