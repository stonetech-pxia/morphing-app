# 「记一笔」预填：规则为主、系统识别补充、版式记忆

日期：2026-10-28。分支 `claude/local-classify-124`。环境是 Linux 云容器，**没有 Mac、iOS 模拟器、Android SDK 和手机**。

## 创始人的决定和这次的做法

另一个会话转来的原始顺序是「系统支持就只用系统识别，不支持才用规则」。创始人 2026-10-28 在本会话里改成：

> 加入版式记忆，修改D-244，系统识别 为辅助和补充，规则为主，做吧，做完推送

所以这次按下面的顺序做：

1. **候选**：日期、金额都以规则（`text-rules` 的写法，加上 `prefill/candidates.ts` 的扩展）为主。
   - 系统识别出同一位置、同一个值时，规则的候选记一笔「对得上」（`confirmed`）。
   - 规则没找到、系统找到的，作为补充加进来。
   - 同一位置两边值不一样时，听规则的。
2. **挑选**：先看版式记忆，学会了的字段按记忆读；读不出再按标签挑。挑不出来就空着。
3. **不预填的字段**：商家以外的自由字段、分类等，没有规则也没有记忆，不预填，也不做大模型预填。
4. **只预填表单**：用户检查后点「记下」才保存（D-187、D-190）。

DECISIONS 的 D-244 已经按这个改了：注明了创始人的原话和日期，状态写的是「命名已定；预填方向已定、未实现，清空和备份待定」，**没有写成已做完**。`docs/TOOLS_DESIGN.md` 加了一段，`CLASSIFY_124_REPORT.md` 的待决定第 3 条也注明已经定了。其余引用 D-244 的地方都是说「命名」那一步，那一步的说法仍然对，没有改。

## 代码（`packages/core/src/prefill/`，纯 TS，未接界面）

- `candidates.ts`：与平台无关的候选类型 `ValueCandidate`，包括：
  - 种类：金额或日期；
  - 统一后的写法：金额是 `1234.56`，日期是 `YYYY-MM-DD`；
  - 原文、行号、行内位置；
  - 来源：`rule` 或 `system`；
  - 两个标记：`confirmed`（规则和系统对得上）、`repaired`（改过形近字）。

  文件里的几个函数：
  - `ruleCandidates`：规则候选。日期加了月份名（`March 2, 2026`、`1er avril 2026`）和两位年份。
  - `repairDigits`：把数字里认成字母的字改回来（`1O7.45`、`2026年S月`）。只在改完像金额或日期的那一段里改，一个字换一个字，位置不变。
  - `systemCandidates`：把系统给的整段位置换成行和行内位置。
  - `mergeCandidates`：按「规则为主、系统补充」合并两边的候选。
  - 英文、法文里连着写、又没有小数的四位整数（`5256 €`）不当金额，因为多半是小数点没认出来。这页的金额都带两位小数时，没有小数的那个也不取。

- `pick.ts`：按标签挑。
  - 金额分四级：
    1. 最终付的：实付、应付、价税合计、Amount paid、Balance due、Total TTC、Net à payer……
    2. 合计：合计、Total、Montant……
    3. 刷卡或扫码的付款行；
    4. 排除的：小计、优惠、找零、现金、税、HT、Remise……；有找零时，「实收」也排除。

    只看最高的一级，这一级只有一个值才填。

  - 标签就在同一行、值的前面；那里只有符号时，看上一行（标签单独一行、两栏被拆开）。
  - 日期：去掉到期、配送、打印、账期这类，剩下只有一个值就填；不止一个值时，只看「开票日期」类标签下的。
  - 税额：标签像税、又不是「不含税 / 含税合计 / 税率」的才取。
- `memory.ts`：版式记忆。下面一节专门讲。
- `prefill.ts` 的 `prefillRecord`：按上面的顺序把一张表的字段填上。没有记忆时，规则只认得出「金额、税额、日期、单号」。表里同一种字段不止一个时（例如两个金额字段），分不清是哪个，就不填。
- 单元测试：`prefill.test.ts` 共 21 个，`text-classify` 和其余测试照常通过。

## 版式记忆（`memory.ts`）

- **从保存的值学**，不是从预填的值学：`learnLayout` 收的是用户点「记下」时最终保存的值。
- **学什么**：
  - 金额和日期记「跟在哪个标签后面（同一行还是上一行）、大约在页面的哪个高度、什么写法」，**不记值本身**；
  - 商家这类不变的文字字段，**记值**，新文件文字里出现同样的值才填；
  - 单号每次不一样，所以永远学不会，仍由规则读。
- **什么时候不学**：
  - 值在文字里找不到出处，不学；
  - 出现几次时，日期分不清就不学；金额只有一处的标签是「实付 / 合计」这一级才认它，否则不学。
- **两次一致才算学会**：前两次保存后才开始用。**用户改了记忆填的值就降级**：从这次看到的重新开始，看不到出处就先不用。
- **认版式**：
  - 主要看标签文字：把几次都出现的标签行留作版式的特征；没有标签的商品行每次不同，不算。
  - 新文件里出现 60% 以上的特征就算同一个版式（拍歪后行连在一起也算）。
  - 同一个标签下有几个不同的值时，才用行框（`recognizeText` 的 items）的位置挑最近的；两个差不多远就空着。
- **表结构变了**：按字段 ID 存，字段删了或者类型变了，那一项就丢掉。

**读错的原因**（都写在这里，没有据此改代码）：

- **双栏**：标签全在前、数值全在后时，记忆里的「标签在同一行或上一行」对不上，记忆读不出。于是退回规则，规则把挨着的数配给了错的标签，4 张读错，**都是规则读错的，不是记忆**。可以考虑「这个版式已经学会、记忆却读不出时，直接空着，不退回规则」。这是要创始人定的取舍。
- **多一行优惠**：`p-zh-07-4` 停车场。前两张没有优惠，「应收金额」和「实收金额」相等，学的时候按标签级别认了「应收」。第 4 张有了停车券，应收 13.00、实收 8.00，记忆读了 13.00，**这是记忆读错的**。根源是「两处值相同时用标签级别认出处」，这一处认错了，而且只看了两张，没法发现。

**和要求的口径不一致的地方**：要求是「学一次，下次新值能读对」，又要求「同一字段两次一致才算学会」。按后者，第一个用上记忆的是第 3 张，不是第 2 张。表里就是按第 3、4 张报的。如果要「学一次就用」，把 `LEARNED_HITS` 改成 1 就行，但读错的可能会多，需要创始人定。

## 原生系统识别（`morph-vision`，只做补充，**没有编译过**）

- **JS**：
  - `modules/morph-vision/index.ts` 加了 `detectData?(text, language, allowDownload)`（返回日期和金额在整段文字里的 UTF-16 位置，日期带 `YYYY-MM-DD`）、`dataDetectionStatus?(language)` 和错误码 `ERR_VISION_NEEDS_DOWNLOAD`。
  - `runtime/detect-data.ts`：**从不下载模型**。系统出任何问题都返回空，预填照样只用规则。结果会再查一遍：位置越界的、日期写法不对的都丢掉。
  - `runtime/expo-vision.ts` 接上了这一层，有 3 个 jest 测试。
- **iOS**（`MorphVisionModule.swift`）：
  - iOS 26 起用 `DataDetection` 框架的 `String.dataDetectorMatches([.moneyAmount, .calendarEvent])`。我从苹果文档的 JSON 接口核对过：`MoneyAmount` 有 `amount: Decimal` 和 `currency`，`CalendarEvent` 有 `startDate`，`Options.documentLanguageCode` 是 `Locale.LanguageCode?`，都是 iOS 26.0 起才有。
  - **金额在 iOS 26 起能识别**，所以「iOS 上只有日期」只对 iOS 26 以前成立。
  - 更早的系统用 `NSDataDetector(.date)`，只认日期。
  - podspec 把 `DataDetection` 设成弱链接。代码用 `#if canImport(DataDetection)` 包起来，旧 Xcode 也能编译。
  - 新版 Vision 的 `RecognizeDocumentsRequest`（iOS 26）也有 `detectedData`，但它的输入是图片，不是文字，没法喂 `ocr.txt`，所以没用它；文字那条路用的是 DataDetection。
- **Android**（新文件 `DataDetection.kt`）：
  - ML Kit 实体识别，`com.google.mlkit:entity-extraction:16.0.0-beta5`，只取 `TYPE_DATE_TIME`（精确到日的）和 `TYPE_MONEY`。
  - **每种语言的模型第一次用时从 Google 下载，不打包进 App。** 没下载、又不许下载时（`allowDownload = false`，JS 一律这样调），或者没网时，以 `ERR_VISION_NEEDS_DOWNLOAD` 结束，App 只用规则。
  - 支持的语言写了中英法德西意葡日韩。
- **没有核对或没有量的**（Google Maven 和 `developers.google.com` 都被网络策略拒绝了）：
  - `entity-extraction` 的版本号；
  - 每种语言的模型多大；
  - APK 增加多少（库本身，不含模型）；
  - 实体识别对中文金额的效果。

  量法和图像分类一样：同一个提交，加和不加这一行依赖各打一个 release 包，比两个 APK；模型大小看第一次下载时的流量，或者 `RemoteModelManager` 下载前后 App 数据目录的大小。

## 三类结论

### 单元测试或桌面 Node 验证过的

- 候选、形近字修正、按标签挑、税额、日期排除、版式记忆的学习、降级、丢弃、行框选择，以及 `prefillRecord`：共 21 个 vitest 测试。
- JS 端的系统识别出错时只用规则、从不下载、去掉坏结果：3 个 jest 测试。
- 上面三张成绩表（477 例开发集、120 条盲测、48 张成对样本）是桌面 Node 上跑的。文字是虚构的模拟 OCR，**不是真实 ML Kit / Vision 的输出**。
- `npm run check` 除 `format:check` 外全部通过；`format:check` 的问题是出发分支上原来就有的，见 `CLASSIFY_124_REPORT.md`。

### 只写了代码，没有编译或没有跑

- iOS 的 `detectData`（DataDetection 和 NSDataDetector）、podspec 的弱链接：Linux 上编译不了。
- Android 的 `DataDetection.kt`、模块里的两个新方法、`entity-extraction` 依赖：没编译，版本没核对，体积和模型大小没量。
- `compare_system.ts`、`export_probe_bundle.ts` 只用假的探针输出走通过。

### 只有模拟器或真机能测的

- 系统识别在 477 份文字上的召回和写法一致性（步骤见上文）。
- iOS 26 和 iOS 18 的差别；Android 模型下载、没网时退回规则。
